SECTION 4: TWO-PHASE UPLOAD — HOW IT WORKS
================================================================================

ENGLISH EXPLANATION:
Uploading a photo happens in two steps. In step 1, the app asks the backend for
a secure temporary URL (a "presigned URL") that points directly to S3. In step 2,
the app uploads the photo file directly to S3 using that URL — the backend never
touches the actual photo data in this step. Once S3 has the file, the app tells
the backend "it's uploaded, please process it." The backend then does all the
heavy work: checking for duplicates, converting formats, extracting dates, and
saving the final record to the database.

PHASE 1 — Get presigned URL:
  POST /api/upload-url
  - Validates event exists
  - Generates staging key: staging/{eventId}/{uuid}.{ext}
  - Returns presigned PUT URL (15-minute expiry)
  Files: src/app/api/upload-url/route.ts

PHASE 2 — Process upload:
  POST /api/upload
  - Backend fetches file from S3 staging key
  - Runs EXIF extraction (extractBestDate)
  - Converts HEIC → JPEG if needed
  - Strips GPS data (privacy)
  - Computes pHash for duplicate detection
  - Checks for duplicates and runs quality upgrade logic
  - Moves file from staging/ to final location
  - Writes record to Supabase photos table
  - Sends upgrade notification if a higher-quality version replaced an old one
  - Timeout: 60 seconds (client-side) — NOT the default 15s
  Files: src/app/api/upload/route.ts

IMPORTANT TIMEOUT RULE:
processUpload() in lib/api.ts uses 60000ms (60s) timeout.
ALL other API calls use the default 15000ms (15s) timeout.
This is because processUpload does pHash + S3 move + DB write which can exceed 15s.

Upload concurrency:
  Individual upload: sequential (one at a time)
  Upload by date: 3 at a time (CONCURRENCY=3)

Pre-check (Upload by date only):
  Before calling backend, app checks if filename already exists in event.
  This is a LOCAL check using cached filenames — no backend call.
  Note: individual upload via image picker may return different filenames than
  Upload by date via MediaLibrary for the same photo (Android system behaviour).
  The backend pHash detection catches these as duplicates anyway.

SECTION 5: PHOTO CLASSIFICATION — dateSource SYSTEM
================================================================================

ENGLISH EXPLANATION:
Every photo is classified into one of two galleries — "Photos Gallery" (main
timeline) or "Other Photos" — based on WHERE its date came from. Photos that
have a verified date from camera EXIF data AND have a camera Make field (like
"Apple" or "samsung") go to Photos Gallery. Everything else (screenshots,
WhatsApp copies, files without full EXIF) goes to Other Photos.

dateSource values:
  "exif"        → Photos Gallery (real camera photo, trustworthy timestamp)
  "file_meta"   → Other Photos (file system date, not trustworthy)
  "upload_time" → Other Photos (no date info at all)

How dateSource is assigned (in src/lib/exif.ts → extractBestDate):
  1. Parse DateTimeOriginal / CreateDate AND the Make field from EXIF
  2. If date found AND Make is present → "exif" (real camera photo)
  3. If date found but NO Make → fall through (screenshot: has date, no camera)
  4. If no EXIF date → "file_meta" from file system creation/modification time
  5. If file stat fails → "upload_time"

Why the Make check matters:
  iOS and Android screenshots embed DateTimeOriginal (time of screenshot) but
  have NO camera Make field. Before the Make check was added (2026-08-13),
  screenshots appeared in Photos Gallery. Real camera photos always have
  Make: "Apple" / Make: "samsung" / etc.

WhatsApp HD photos:
  In ~99% of cases, WhatsApp strips EXIF entirely → dateSource = "file_meta"
  → Other Photos (already correct). In ~1% of cases WhatsApp preserves full
  EXIF including Make → treated as real camera photo. Acceptable.

belongsInMainTimeline(dateSource):
  Returns true only for "exif". Used to decide which gallery a photo goes in.

SECTION 6: DUPLICATE DETECTION AND QUALITY UPGRADE
================================================================================

ENGLISH EXPLANATION:
When a photo is uploaded, the backend computes a "perceptual hash" (pHash) —
a compact fingerprint of what the image looks like. It then compares this
fingerprint against all existing photos in the event. If two photos look very
similar (within a Hamming distance threshold), they're considered duplicates.
Instead of rejecting the new photo, the system checks which version is better
quality (higher resolution, bigger file size) and keeps only the best one.

Files: src/lib/duplicate-detection.ts

pHash computation:
  - Resize to 32×32 grayscale
  - Apply DCT (discrete cosine transform)
  - Compare pixel values to mean → binary hash
  - Result: 64-bit hash stored as hex string

Hamming distance:
  How many bits differ between two pHash values.
  Lower = more similar. Threshold varies by scenario (see below).

isDuplicate logic — three scenarios based on dateSource:

  bothHaveExif (both are real camera photos):
    - Hamming distance ≤ 10 AND timestamp gap ≤ 2 seconds → duplicate
    - Hamming distance ≤ 10 AND timestamp gap > 2 seconds → NOT duplicate
      (burst shot protection — different frames, same scene)
    - Hamming distance > 10 → NOT duplicate

  oneHasExif (one real camera, one WhatsApp/processed copy):
    - Hamming distance ≤ 10 → duplicate
    - Hamming distance > 10 → NOT duplicate

  neitherHasExif (both screenshots/processed):
    - Hamming distance === 0 (pixel-perfect match) → duplicate
    - Hamming distance > 0 → NOT duplicate (different screenshots)

Quality upgrade (resolveDuplicate — keep_new):
  When a duplicate is found, pick the BETTER version:
  - "exif" source always beats "file_meta" / "upload_time" on trustworthiness
  - Between same dateSource: larger file size wins
  - A screenshot can NEVER replace a real camera photo
  - The winning photo replaces the existing one in S3 and DB
  - The original uploader receives a server notification: "your photo was
    replaced by a higher quality version"

SECTION 7: GPS STRIPPING (PRIVACY)
================================================================================

ENGLISH EXPLANATION:
Before saving any photo to S3, the backend removes all GPS location data from
the EXIF metadata. This is a privacy measure — guests should not have their
precise location exposed to strangers via photo metadata.

Function: stripGpsExif() in src/lib/image-processing.ts
  - Reads EXIF bytes from JPEG
  - Removes GPS IFD data
  - Rewrites EXIF without GPS
  - All other EXIF (dates, camera make, etc.) preserved
  - Called during processUpload before final S3 write

SECTION 8: OTP VERIFICATION (WhatsApp)
================================================================================

ENGLISH EXPLANATION:
When a user tries to log in or register, the app sends their phone number to the
backend. The backend generates a random 6-digit code, stores it in the database
with a 5-minute expiry, and sends it to the user via WhatsApp using Meta's
Cloud API. The user enters the code in the app. The app sends the code to the
backend to verify. If it matches and hasn't expired, the user is authenticated.

Backend:
  POST /api/native/otp/send
  - Generates 6-digit code
  - Stores in otp_codes table with 5-minute expiry
  - Sends via Meta Cloud API WhatsApp template: momentsinframe_otp

  POST /api/native/otp/verify
  - Checks code matches and hasn't expired

App functions (lib/api.ts):
  sendOtp(phone) — throws if backend returns error
  verifyOtp(phone, code) — throws if backend returns error

  9. Results returned as two arrays: photos (dateSource=exif) and otherPhotos
  10. Results displayed in two-section screen, oldest first
  11. User can drag-to-select and download (no delete on this screen for anyone)

SECTION 10: UPLOAD — INDIVIDUAL UPLOAD AND UPLOAD BY DATE
================================================================================

ENGLISH EXPLANATION:
There are two ways to upload photos. "Individual upload" uses the system image
picker (like any other app's file chooser) — the user taps Upload Photos and
selects up to 40 photos from any album. "Upload by date" lets the user pick a
calendar date and automatically uploads all camera photos from that day.

The filename problem:
  On Android, the system image picker sometimes renames files to generic IDs
  (e.g., "43911.jpg") instead of using the original filename (e.g.,
  "20260614_190514.jpg"). Upload by date uses MediaLibrary directly and always
  gets the original filename. This means the pre-check in Upload by date may
  not recognise photos already uploaded individually (filename mismatch).
  The pHash backend catches them as duplicates anyway — no wrong data is stored.
  Status: PARKED — harmless in practice.

Individual upload (app/event.tsx → Upload Photos button):
  - System image picker, up to 40 photos
  - Sequential upload
  - Shows duplicate/upgrade review popup after

Upload by date (app/event.tsx → Upload by date option):
  - User selects date from calendar
  - App scans Camera roll for all assets on that date
  - Pre-check: skips filenames already in event (local check, no backend call)
  - Uploads remaining 3 at a time (CONCURRENCY=3)
  - Backend duplicate detection still runs on each

SECTION 15: PHOTO DOWNLOAD LOGIC
================================================================================

ENGLISH EXPLANATION:
Single photo download: app asks backend for a temporary secure download link
(presigned S3 URL), then downloads it and saves to device gallery.
Bulk download: app asks backend to prepare a ZIP file on the server, then
downloads the ZIP to device.

Single photo:
  POST /api/native/photos/{photoId}/download-url
  Returns presigned S3 download URL (1-hour expiry)
  App downloads file and saves to gallery using photo-saver native module

ZIP download (>40 photos or user selects ZIP option):
  POST /api/native/events/{slug}/prepare-zip
  Backend creates ZIP on server from S3 photos
  Returns ZIP URL for download

Photo-saver native module (modules/photo-saver/):
  Saves downloaded photo to device gallery WITH original EXIF metadata
  Includes original filename, correct date in gallery
  MUST be listed in package.json or requireNativeModule returns null at runtime

SECTION 18: IN-APP CAMERA (SPEC FINALISED — CODING NOT STARTED)
================================================================================

ENGLISH EXPLANATION:
The app will have a built-in camera screen where users can take photos with live
colour filters applied in real time. After taking a photo, they see a preview
and can choose to upload it to the current event (and save to their gallery).
This sits alongside the existing "Upload Photos" (choose from library) option.

ENTRY POINT:
  On Event screen: two buttons side by side —
    "Take Photo" (dark outlined, left)
    "Upload Photos" (yellow, right)
  Helper text below both buttons

CAMERA SCREEN LAYOUT (top to bottom):
  1. Top bar: X (close) + flash toggle only
  2. 3:4 viewfinder — fixed ratio, live filter applied in real time
  3. Filter section: category tabs + horizontal scrollable filter strip
  4. Bottom row: last gallery photo (left) | capture button (centre) | flip camera (right)

FILTER CATEGORIES AND TABS:
  Classic | Aesthetic | Film (tabs above the filter strip)

FILTER THUMBNAILS:
  - Static pre-baked sample photo with each filter's colour matrix applied
  - Circular thumbnails in the horizontal strip
  - NOT coloured dots, NOT live frame previews (GPU overhead not worth it)
  - Selected filter has white border ring
  - Sample photo: warm outdoor scene, works across all 20 filter styles
  - Thumbnails can be updated via OTA (no rebuild needed)

AFTER CAPTURE:
  - Full-screen preview screen with the captured photo
  - Two buttons at bottom: Retake (dark) | Post (white)
  - Post → saves to device gallery AND uploads to current event

OTHER DECISIONS:
  - Flash: on/off/auto toggle — works on both iOS and Android
  - No intensity slider — full strength on single tap (slider possible via OTA later)
  - No Live Photos — Apple restricts this to native camera; user confirmed this is fine
  - Captures standard JPEG/HEIC with filter colour matrix baked in
  - Works on all phone brands — iOS and Android

TECH STACK (for this feature):
  - Camera: react-native-vision-camera v5 (upgrade from current expo-camera)
  - Filters: @shopify/react-native-skia colour matrix frame processor
  - Worklets: react-native-worklets-core (for off-thread processing)
  - iOS build image: macos-tahoe-26.5-xcode-26.6 (required for VisionCamera v5)
  - All processing on-device GPU — zero API cost, zero licensing fee

THE 20 FILTERS (colour matrices — completely free):

  CLASSIC (8 filters):
    1. Normal       — No filter (identity matrix)
    2. Warm         — Golden/cozy, boosts reds and oranges
    3. Cool         — Fresh/airy, boosts blues
    4. Vivid        — Punchy, saturated
    5. Fade         — Matte/faded aesthetic
    6. B&W          — Classic black and white (desaturation matrix)
    7. Drama        — High contrast, moody, deep shadows
    8. Vintage      — Warm + faded + slight vignette

  AESTHETIC (8 filters):
    9.  Golden Hour   — Deep orange warmth, like sunset on skin
    10. Sunset        — Pink + orange tones, popular for portraits
    11. Teal & Orange — Cinematic look (hugely popular, used in movies)
    12. Moody         — Dark, desaturated, cool shadows
    13. Soft          — Gentle pastel brightening, dreamy
    14. Rose          — Subtle pink warmth, flattering for skin
    15. Forest        — Cool green tones, outdoorsy
    16. Matte         — Flat, no blacks, popular on Instagram Reels

  FILM (4 filters):
    17. Kodak         — Warm, slightly faded, slight yellow in highlights
    18. Fuji          — Cool greens in shadows, clean whites
    19. Cinematic     — High contrast, crushed blacks, slight blue
    20. Lo-Fi         — Oversaturated, high contrast, retro feel

Filters are colour matrix values in JS → new filters can be added via OTA after
the build ships. No native recompilation needed to add more filters.

SECTION 19: TRUSTED CIRCLE (SPEC FINALISED — CODING NOT STARTED)
================================================================================

ENGLISH EXPLANATION:
Trusted Circle lets guests in an event make their photos visible only to people
they personally trust, rather than everyone in the event. It's opt-in per event
(organiser enables it). Guests can invite each other to their circle — both must
accept before either can see the other's restricted photos. Organisers and
co-admins always see everything regardless.

Full 24-rule spec:

CORE RULES:

1. WHAT IS A TRUSTED CIRCLE?
   A private circle of guests within a single event. Completely contained —
   no data exists outside the event.

2. OPT-IN PER EVENT — OFF by default. Organiser must explicitly enable it.

3. ORGANISER TOGGLE — "Trusted Circle" in SETTINGS section of Manage Event
   (4th toggle, below "View only event"). Description is dynamic:
   OFF state: "Guests can create private photo circles"
   ON state:  "Active — private circles enabled"

   Alert when ENABLING:
     Title: "Enable Trusted Circle?"
     Message: "Guests can make their photos visible only to guests they've
     personally connected with. Both must accept the invite before they can
     see each other's restricted photos. Organisers and Co-Admins always see
     all photos."
     Buttons: Cancel | Enable

   Alert when DISABLING:
     Title: "Disable Trusted Circle?"
     Message: "All restricted photos will become visible to everyone in the
     event. Guest circle connections will be preserved — re-enabling will
     restore them instantly. Organisers and Co-Admins are not affected."
     Buttons: Cancel | Disable

4. SENDING AN INVITE — Guest A sends invite to Guest B. Both must be in the
   same event. Only available when Trusted Circle is enabled. Uses contacts
   to show which contacts are in the same event.

5. ACCEPTING — Guest B gets a bell notification. Can accept or decline from
   the ⋮ menu on the event screen.

6. MUTUAL ACTIVATION — Circle activates only when BOTH have accepted.

7. ONE-TO-ONE — A↔B and A↔C are completely separate circles.

8. PHOTO VISIBILITY — Each guest has ONE visibility setting for ALL their
   photos in the event: public (everyone) or restricted (trusted circle only).

9. DEFAULT — Public. Guests must actively choose to restrict.

10. EMPTY CIRCLE RULE — If a guest has 0 accepted connections, their photos
    stay public regardless of any restriction setting. If they try to restrict
    with empty circle, show warning:
    "Your photos will be hidden from all guests until you add trusted connections."

11. BACKDATED ACCESS — Connecting later gives immediate access to all past
    photos too.

12. ORGANISER UPLOADS — Always visible to everyone. No restriction possible.

13. CO-ADMIN UPLOADS — Always visible to everyone. Same as Organiser. No
    restriction possible.

14. ORGANISER — Always sees every photo regardless of visibility setting.

15. CO-ADMINS — Always see every photo regardless of visibility setting.
    Co-Admins do NOT see the Trusted Circle menu on the event screen (only
    shown to regular guests).

PENDING INVITE EDGE CASES:

16. B NOT YET REGISTERED — Invite stored as pending in DB. When B joins the
    event, they see it in their bell notification immediately. If B never joins,
    invite stays pending indefinitely but never activates.

LOGOUT / DELETE EDGE CASES:

17. GUEST LOGS OUT — Photos revert to public immediately. Circle connections
    preserved in DB. On log back in, they can re-restrict manually.

18. GUEST DELETES ACCOUNT — Account becomes "Unknown user", photos remain in
    event. Photos revert to public. Circle connections removed.

CO-ADMIN ROLE CHANGE MID-EVENT:

19. GUEST PROMOTED TO CO-ADMIN — Immediately sees all photos including
    restricted ones. Their own photos become public (Co-Admin = always public).
    Trusted Circle menu disappears. Any pending circle invites they sent/received
    are cleared.

20. CO-ADMIN DEMOTED TO GUEST — Loses Co-Admin privileges; restricted photos
    hidden again. Their photos revert to public (safe default). Trusted Circle
    menu reappears. They start fresh — no circle connections, can build them.

KEY PRINCIPLE: Role change or account change = photos revert to public,
state resets cleanly.

TOGGLE OFF (DORMANT MODE):

21. TOGGLE OFF — All photos become visible to everyone (feature paused). Circle
    connections preserved in DB. If re-enabled, circles restore instantly and
    guests can re-restrict.

UI PLACEMENT:

22. EVENT SCREEN — "Trusted Circle" option in the ⋮ menu. Only shown to regular
    guests when Trusted Circle is enabled for the event.

23. TRUSTED CIRCLE PANEL — Pending requests shown on top, trusted members below.
    Same visual design as Manage Guests panel on Manage Event page.

LIFECYCLE:

24. EVENT DELETED — All trusted circle data, connections, and visibility settings
    deleted. Nothing persists.

NOTE: Trusted Circle was previously called "Phase 4" in early planning. The spec
in memory supersedes the older Phase 4 notes about "forever trusted circles" and
"event trusted circles". The current final spec is event-scoped only (rules 1-24).

SECTION 20: SELF-SERVE EVENTS / PHASE 3 (SPEC FINALISED — CODING NOT STARTED)
================================================================================

ENGLISH EXPLANATION:
Currently, only Akriti (the master admin) can create events. Phase 3 changes this
so any user who downloads the app can create and manage their own events. When
registering, users choose whether they want to be an Organiser (create events) or
a Guest (join events). Organisers get a full event management dashboard.

REGISTRATION FLOW:
  1. Name + phone number (same as today)
  2. OTP verification via WhatsApp (backend built, UI to be shown)
  3. Choice screen: Organiser or Guest

  IF GUEST selected:
    → Opens directly to Enter Event Code page
    → Everything from there works as today
    → Back arrow returns to Organiser/Guest choice screen

  IF ORGANISER selected:
    → Create master/organiser password
    → Goes to All Events page (manage their own events)
    → Back arrow returns to Organiser/Guest choice screen

ADMIN MODEL:
  - Organiser who creates an event is automatically admin — linked by phone number
  - No separate admin login button needed
  - Event Admin Login button REMOVED entirely
  - App recognises organiser/co-admin automatically from phone number

ALL EVENTS PAGE (new screen):
  - Shows only events the organiser created (NOT co-admin events)
  - Shows: event name, date, guest count, and other existing info
  - Co-admin events do NOT appear here

CO-ADMIN FLOW:
  - Organiser adds phone number as co-admin from Manage Event screen
  - Backend checks if that number is registered:
    - If YES → push notification: "You've been made co-admin of [Event Name]"
    - If NO → SMS/WhatsApp: "You've been added as co-admin, download: [link]"
      (when they register with that number, app auto-recognises them as co-admin)
  - Co-admin accesses event via guest flow (enter event code)
  - App sees their phone number, gives admin toolbar automatically

CO-ADMIN PERMISSIONS:
  - Exactly what today's Event Admin Login gives — no more, no less
  - Cannot add other co-admins (only the organiser can)
  - Cannot delete the event (only the creator/organiser can)
  - No OTP required to become co-admin (number already verified at registration)
  - Organiser can remove co-admins anytime — access revoked immediately

OPEN VS CLOSED EVENTS:
  - Open: anyone with the event code can join (same as today)
  - Closed: organiser manually adds phone numbers; only those can join
  - Stored as: is_closed boolean default false on events table

GUEST DELETE TOGGLE:
  - Toggle: "Allow guests to delete their own photos" — ON by default
  - Stored as: allow_guest_delete on events table
  - Co-admins and organiser ALWAYS have delete regardless of this toggle

APP STATE MEMORY:
  - App remembers last mode — reopens directly to guest home or organiser events
  - Back arrow on home screens returns to Organiser/Guest choice screen anytime

WEB APP (same changes apply to both):
  - Identical registration flow changes needed on web (momentsinframe.com)
  - Identity-based admin toolbar (remove manual organiser login)
  - Both apps updated in parallel

MONETISATION (PARKED — Phase 3 plan):

  - In-app storage purchase (e.g., 10GB for ₹199) via IAP

SECTION 21: PUSH NOTIFICATIONS (NOT BUILT — SPEC FINALISED)
================================================================================

ENGLISH EXPLANATION:
Push notifications are planned but not yet built. The app currently uses server
notifications (poll-based, bell icon) for in-app alerts. Push would deliver alerts
to the device even when the app is closed. The scope is intentionally narrow —
only 4 specific types that are infrequent and personally relevant.

WILL NOT add push notifications for new photo uploads — events with 100+ people
uploading every 10-15 minutes would be unacceptably noisy.

THE 4 APPROVED NOTIFICATION TYPES:
  1. Co-admin added / removed — notify the affected user
  2. Photo replaced by higher quality — notify the original uploader
  3. Event expiring in 24 hours — notify the organiser to extend
  4. Event closed / reopened — notify guests

WHAT NEEDS TO BE BUILT:
  - Store Expo push token in Supabase when user joins/opens an event
  - Backend sends push via Expo Push API for each of the 4 trigger points
  - The server notification infrastructure (Supabase table + API routes) is
    already in place — push is just a delivery layer on top

SECTION 29: EVENT EXPIRY BEHAVIOUR
================================================================================

ENGLISH EXPLANATION:
When an event's expiry date passes, different roles lose different levels of
access. The organiser never loses control of their event.

When an event expires:
  - Guests:     Lose access entirely. Cannot view, upload, or download.
  - Co-Admins:  Can only VIEW and DOWNLOAD photos. Cannot upload or manage.
  - Organiser:  FULL ACCESS retained. Can delete, download, and view everything.
                Can also extend the event from Manage Event to restore guest access.

Frontend check (app/event.tsx):
  const isEventExpired = expiresAt ? new Date(expiresAt) < new Date() : false;
  This is a client-side check using the expiresAt string from the event record.

    the app exits select/delete mode first, then activates the filter.

Code: app/event.tsx — myUploadsFilter state controls all of the above.

SECTION 32: ACCOUNT DELETION BEHAVIOUR
================================================================================

ENGLISH EXPLANATION:
When a user deletes their account, their personal record is removed but their

SECTION 33: EXIF TIMEZONE HANDLING — DO NOT TOUCH
================================================================================

ENGLISH EXPLANATION:
Whatever time the phone displays when a photo is taken is exactly what the app
shows — for photos taken anywhere in the world. An Indian photo taken at 9:18 PM
shows as 9:18 PM. A Thai photo taken at 4:55 PM shows as 4:55 PM. Verified by
real uploads (2026-08-14).

How the code achieves this (backend: src/lib/exif.ts):
  - exifr.parse() is called with ONLY ["DateTimeOriginal", "CreateDate", "Make"]
  - OffsetTimeOriginal is deliberately NOT requested
  - Without an offset, exifr cannot do timezone conversion — it returns the raw
    local time exactly as written in the EXIF
  - The backend then subtracts 5.5 hours before storing

How display recovers the original time (frontend: app/event.tsx line ~2568):
  new Date(taken_at).toLocaleString('en-IN', { timeZone: 'Asia/Kolkata', ... })
  - This adds 5.5 hours back (IST conversion)
  - The −5.5h on save and +5.5h on display cancel out perfectly
  - Result: original EXIF local time is always shown, regardless of country

Hidden dependency — Vercel server must be in UTC:
  The cancellation works because Vercel runs in UTC. On a UTC server, exifr
  treats the raw EXIF local time string as UTC (no conversion applied).
  On a developer's IST machine, exifr converts IST→UTC first, then the backend
  subtracts 5.5h again — causing local test results to show wrong times.
  LOCAL TESTING OF THE EXIF PATH WILL SHOW WRONG TIMES. This is expected.
  Trust production behaviour only.

!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!
DO NOT CHANGE ANY OF THE FOLLOWING WITHOUT A FULL IMPACT ANALYSIS:
  1. The istOffsetMs subtraction in src/lib/exif.ts
  2. The timeZone: 'Asia/Kolkata' in the frontend display
  3. Adding OffsetTimeOriginal to the exifr parse tag list

Any change to one side MUST be paired with a matching change on the other side
PLUS a DB migration to add/subtract 5.5h from ALL existing taken_at rows.
Removing either the −5.5h or the +5.5h alone will break display for all photos.
!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!

Cross-timezone events (e.g., photos from Thailand and India in the same event):
  Each photo shows its own local time. Photos sort correctly by date since
  different-country photos are typically on different calendar dates.
  Same-day photos from two countries will sort in the correct real-time order
  (the stored values preserve chronological order even though they are not
  true UTC). For MomentsInFrame's use case (single-occasion events), this is
  not a practical issue.
